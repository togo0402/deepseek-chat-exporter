# 设计说明

这份文档记录 DeepSeek 对话导出助手的实现思路和关键取舍。只是想用的话看 [README](../README.md) 就够了。

## 一、目标与边界

把 `chat.deepseek.com` 上**当前打开的这个对话**导出成一份 Markdown，用户和 AI 的内容都保留。进阶诉求有两个：能只导出其中几轮，以及能选择是否保留 AI 的深度思考。

明确不做的事：批量导出多个会话、删除会话、把数据发往任何第三方。

## 二、数据来源：走接口，不扒 DOM

导出内容有两条路可走：解析页面 DOM，或者调用网页端自己的接口。这里选了后者，原因有三条：

1. **深度思考在 DOM 里不可靠**。页面上思维链通常是折叠的，甚至根本不渲染进 DOM（取决于用户的展开状态）。接口返回的 `fragments` 里，`THINK` 是一段独立完整的内容，开关起来干净利落。
2. **不用猜谁说的话**。接口数据里 `role` 字段明确区分 `USER` / `ASSISTANT`，不需要靠 DOM 结构或样式类名去推断。
3. **保真度更高**。DOM 取到的文本可能已经丢掉了原始换行、代码块围栏的空格等格式信息。

代价是**依赖网页接口的稳定性**。这不是公开 API，DeepSeek 随时可能调整，届时要跟着更新。

好消息是接口调用不需要额外的网络权限——`fetch` 的目标与当前页面同源（`chat.deepseek.com` → `chat.deepseek.com`），没有 CORS 问题，因此**不需要 background service worker**。`src/api.js` 独立成一个模块，就是为了将来万一要改成 `chrome.runtime.sendMessage` 转发时，改动只局限在这一个文件里。

## 三、数据结构

会话历史来自 `GET /api/v0/chat/history_messages?chat_session_id=<id>`，响应形如：

```js
{
  code: 0,
  data: {
    biz_data: {
      chat_session: { id, title, ... },
      chat_messages: [
        {
          message_id,                 // 递增的数值 id
          role: "USER" | "ASSISTANT", // 注意是大写
          inserted_at,                // 时间戳
          fragments: [
            { type: "REQUEST"  | "RESPONSE" | "THINK" | "TIP", content }
          ]
        }
      ]
    }
  }
}
```

几个要点：

- **会话标题、全部消息、深度思考都在这一个响应里**，不需要额外请求列表接口。
- `REQUEST` 是用户提问，`RESPONSE` 是 AI 回答，`THINK` 是深度思考，`TIP` 是页面提示（如「正在生成中」），导出时丢弃。
- **判角色只信 `role` 字段，`fragments` 只用来取内容**。理论上 USER 消息带 REQUEST、ASSISTANT 带 RESPONSE + THINK，但依赖这个规律不如直接读 `role` 稳妥。

请求需要带上 `Authorization: Bearer <token>` 以及一组 `x-client-*` 请求头。token 从页面自己的 `localStorage` / `sessionStorage` 里取——它会以多种形态存在（裸串、被 JSON 包裹、带 `Bearer ` 前缀），所以要按 key 名含 `token` / `auth` 逐个尝试并归一化。

### 容错

`extractChatMessages()` 先走上面这条确定路径；取不到就遍历整棵响应树，找「元素带 `fragments` 数组」的那个数组。接口多包一层 `data` 这类小改动不会立刻把功能打死。

## 四、当前会话 ID 怎么拿

对话页地址形如 `https://chat.deepseek.com/a/chat/s/<session_id>`，正则提取即可。

麻烦的是 **SPA 路由**：点侧边栏切换对话时，页面只调 `history.pushState`，不刷新页面、也不触发 `popstate`。

这里有个常见的坑：**content script 跑在隔离世界里，改写 `history.pushState` 拦不到页面自己发的调用**——两个 world 各有各的 JS 绑定，你改的是你这边的那个函数。所以「覆写 pushState」这套写法在这里无效。

实际用的是三层叠加：

1. **Navigation API**（Edge / Chrome 102+）—— `navigation` 的 `navigate` 事件对同文档导航也会触发，且隔离世界可用。
2. **`popstate` + `hashchange`** —— 覆盖浏览器前进后退。
3. **500ms 轮询比对 `location.href`** —— 最笨但永远有效，作为最终保底。

### URL 里没有 id 时

这几乎总是「新对话」页面，此刻并没有可导出的内容。但用户也可能刚发完第一条消息、URL 还没更新，所以先短轮询等 1.5 秒，再退到侧边栏里找被标记为 `aria-current="page"` 的链接读它的 `href`。都不行就明确提示「请先发送一条消息」。

**绝不按标题去猜会话。** 会话列表接口按 `updated_at` 排序，用户刚在别的标签页聊过天的话，第一条根本不是当前对话——那会静默导出别人的会话，是最糟的体验。

## 五、轮分组

一轮 = 一条用户提问 + 紧随其后、直到下一条用户消息之前的全部 AI 回复。

```
按时间 → message_id → 原始下标的顺序排好
丢掉正文和思考都为空的消息（纯 TIP、空消息）

遍历：
  用户消息   → 若当前轮是「先冒出来的孤立 AI」，并进去；否则收尾当前轮、新开一轮
  AI 消息    → 追加到当前轮；若还没有当前轮，新开一个标记为「无提问」的轮
  其它角色   → 保守收纳，默认不导出
```

排序用**两级比较器**：`inserted_at` 优先，`message_id` 次之，最后用原始下标兜底。不要只按 `Number(message_id)` 相减——一旦 id 换成 UUID 形态，相减会得到 `NaN`，排序结果随机。

各类异常情况的处理：

| 情况 | 处理 |
|---|---|
| 连续两条提问 | 各成一轮，前一轮没有回答，保留不合并 |
| 连续两条 AI 回复（重新生成、分段输出） | 并入同一轮，导出时用空行连接 |
| 首条就是 AI | 形成一个「没有提问的轮」，正常展示和导出 |
| 只有思考、没有正文 | 不丢；关掉思考开关后该条变空，导出时跳过 |
| 消息顺序错乱 | 排序修复 |
| 某一轮没勾选 | 跳过，但**保留原始编号**，导出「第 2 轮」「第 5 轮」便于和面板对照 |

轮的勾选态由「提问」和「回答」两个子项派生，不单独存字段，避免出现「父勾了子没勾」这种不一致。半选状态（`indeterminate`）在每次重建 DOM 后用 JS 补上——这个属性无法用 HTML 表达。

## 六、Markdown 输出与转义取舍

````markdown
# 会话标题

> 来源：https://chat.deepseek.com/a/chat/s/abc123
> 导出时间：2026-10-16 18:20:33 (GMT+8)
> 导出轮数：2 / 共 2 轮

---

## 第 1 轮

**用户**

CSV 里有中文乱码怎么解决？

**AI**

<details>
<summary>深度思考</summary>

用户问的是编码问题，应该先确认文件本身的编码……

</details>

大概率是编码问题，指定编码即可：

```python
df = pd.read_csv("data.csv", encoding="utf-8-sig")
```
````

三处转义决策，各有理由：

**标题** —— 折叠换行并剥掉行首的 `#`。标题来自接口，不能让它破坏文档结构。

**正文原样输出，不转义** —— 这是刻意的。AI 的回复本身就是 Markdown（代码块、表格、公式），一旦转义就会全部毁掉。代价是：用户提问如果以 `#`、`>`、`-`、`1.` 开头，在渲染时会被当成标题、引用或列表。要彻底解决得逐行判断是否在代码围栏之内再加转义，复杂度和出错概率远大于这点观感损失，所以选了保真。

**深度思考内容必须转义 `&` `<` `>`** —— `<details>` 在 CommonMark 里属于 type-6 HTML block，内容按原始 HTML 解析。思考文本里只要出现 `<` 或 `</details>`，就会破坏标签闭合，甚至把后面的正文全吞进去。转义之后 GitHub 上仍正确显示为 `<` `>`。

另外两个细节：

- **不做全局的连续空行压缩**。看着整洁，但会把代码块内部的空行一起吃掉，属于隐性破坏数据。改成按块拼接，块之间正好一个空行。
- **不加 BOM**。加了反而会让某些 Markdown 解析器把开头的 `#` 当成正文。

文件名去掉 Windows / macOS 的非法字符、开头的点号，截断 80 字，兜底 `deepseek-chat`。不强制拼会话 id——用户想要的是「像对话名字的文件」，重名时浏览器会自己加 `(1)`。

## 七、面板交互

```
#dsex-root                      fixed 铺满视口；pointer-events: none
├── #dsex-fab   「导出」悬浮按钮   pointer-events: auto
└── #dsex-mask  全屏遮罩（仅打开时存在）
    └── 对话框
        ├── 头部：标题 + 会话名 + ×
        ├── 工具栏：全选 / 全不选 | ☑保留深度思考 | 已选 N / M 轮
        ├── 列表：每轮 = 复选框 + ▸展开 + 轮号 + 预览
        │    └── 展开后：☑用户 · 预览   ☑AI · 预览   (含深度思考)徽标
        └── 底部：取消 | 导出 Markdown
```

用模态遮罩而不是页面上的浮动条：勾选轮次是个需要专注的任务，遮罩能避免误点页面内容。遮罩只在打开时存在，关闭后不留痕迹。

渲染策略很朴素：**改 state → 整体重建 `#dsex-ui` 的 `innerHTML`**。面板最多几十轮，重建足够快，比手写 DOM diff 更不容易出 bug。两个配套细节：

- 事件监听**委托在 `#dsex-root` 上只绑一次**，所以重建 innerHTML 不会丢事件。
- 重建前存、重建后恢复 `.dsex-list` 的 `scrollTop`，否则每次勾选面板都会跳回顶部。
- 面板里预览的是**原始 Markdown 文本**，插入前必须转义，否则等于 XSS 自己。

「保留深度思考」做成全局开关而不是每轮独立勾选：需求上它就是个全局选项，做成全局能省掉为每个思考片段维护勾选位的复杂度，也符合使用直觉。

## 八、错误处理

统一成有人话的错误提示，**不用 `alert`**（阻塞、打断），改用面板内联错误区加悬浮 toast。

| 场景 | 提示 |
|---|---|
| 未登录 | 未检测到登录状态，请先登录并刷新页面 |
| token 失效 | 登录已过期，请重新登录后刷新页面 |
| 新对话没有 id | 当前是新对话，请先发送一条消息后再导出 |
| 接口结构变了 | 无法解析会话数据，接口可能已更新（同时 `console.warn` 原始响应，便于反馈） |
| 对话为空 | 该对话暂无消息，禁用导出按钮 |
| 网络异常 | 网络请求失败，请检查网络后重试 |
| 导出期间切换了会话 | 面板顶部插提示条「页面已切换到其它对话」+「重新加载」，**不丢弃用户已做的勾选** |

还有一个容易被忽略的竞态：**关掉面板后快速重开**，上一次还没返回的请求会把旧对话的数据写进新面板。用一个自增的 `openToken` 解决——每次打开面板自增，异步结果返回时若 token 已变就直接丢弃。

## 九、MV3 的注意事项

- **注入时机**用 `document_idle`。扩展不做请求拦截，只在用户点击时取数，晚注入没有影响，还能保证 `document.body` 已存在。
- **重复注入防护**：`boot()` 开头判断根节点是否已存在。
- **样式隔离**用「唯一 id + 高权重选择器」而不是 Shadow DOM。manifest 里的 `css` 由浏览器注入，不受页面 CSP 的 `style-src` 限制；而 Shadow DOM 内部得靠内联 `<style>`，反而可能被 CSP 拦下。
- **避开会被 CSP 拦的写法**：不用 `eval` / `new Function`，不往页面注入 `<script>` 标签，不用行内 `onclick=`，一律 `addEventListener`。
- **`pointer-events` 分层**：根节点铺满视口但设为 `none`，只有按钮、遮罩、toast 这些真正需要交互的元素打开 `auto`。因为 `pointer-events` 不是继承属性，中间层必须显式声明，否则会挡住整个页面。
- **扩展重载后的残留脚本**：重载扩展后旧 content script 里的 `chrome.*` 立刻失效，抛 `Extension context invalidated`，但定时器还活着，控制台会一直刷错误。轮询前先检查 `chrome.runtime?.id`，失效就清理定时器并移除根节点。

### 权限

`permissions` 是**空数组**。下载走 `Blob` + `URL.createObjectURL` + `<a download>`，不需要 `downloads` 权限；请求同源，不需要额外的网络权限。这是发布到商店时最小的权限面，也是这个项目刻意保持的卖点。

## 十、图标

manifest 的 `icons` 只接受 PNG 等位图，不接受 SVG。但省略 `icons` 字段扩展照样能加载（显示默认拼图）。

做法是：`icons/icon.svg` 作为可读可改的设计源提交；`scripts/make_icons.py` 用 **Python 标准库**生成三个尺寸的 PNG——手写 PNG 容器（`struct` 组块 + `zlib` 压缩），几何图形纯数学光栅化，不需要 Pillow，也不需要字体。生成结果直接提交进仓库，所以普通用户 clone 下来就能加载，**零构建步骤**。

16px 下细线会糊，所以三个尺寸分别硬编码线宽，不做等比缩放。

没有走 Node 那条路（`sharp` / `resvg` 之类），因为那会引入原生二进制依赖，对一个「零依赖零权限」的扩展来说太重。

## 十一、测试策略

最大的困难是**核心逻辑依赖登录态**，而登录态没法自动化。所以把「轮分组」和「Markdown 生成」这两块抽成不碰 DOM 的纯逻辑模块，用 Node 的 `vm` 造一个带 `window` 的沙箱跑起来：

```bash
node tests/run.mjs
```

零依赖，不需要装任何东西。覆盖的边界情况包括连续提问、连续 AI 回复、首条就是 AI、只有思考没有正文、纯 TIP 与空消息、消息乱序、思考内容含尖括号、只导出部分轮等。

另一部分——真实接口能不能调通、按钮在页面上长什么样——只能人工在浏览器里验证。

## 十二、已知风险

- **接口变更**。三处兜底可以扛住小改动：遍历响应树找消息数组、标题三级回退、出错时打印原始响应。但接口大改仍需要更新扩展。
- **排序一致性**。如果将来接口的时间戳精度降到秒，同一秒内的消息只能靠 `message_id` 兜底——两级比较器已经覆盖，但需要真实数据回归。
- **提问被误解析**。见第六节的转义取舍。
